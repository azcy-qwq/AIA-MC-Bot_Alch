# 钻石护甲消失调查（2026-11-15）

## 当前结论

钻甲目前确实不在背包或装备栏。**尚不能确定最终去向**。已复现一个与该时间窗口吻合的本地停机缺陷，可能导致角色无人控制留在服务器上，但不能据此直接认定钻甲已被打坏。

## 日志证据（北京时间）

- 最后一个有 Worker 的钻甲快照：2026-11-15 17:21:50，PID 17108，位置 [-68.5,66,279.9]，四件钻甲 durability_used 均为256。
- 停机后 workerPid=null 的记录重复旧 UI 快照，不是新的游戏背包确认。
- 第一个有新 Worker 的空护甲栏快照：2026-11-15 17:27:51，PID 10904，四栏均空；背包也无钻甲，原备用铁甲、16散钻和钻石镐仍在。
- 更早记录中四件钻甲已损耗耐久曾从3增长至256，期间发生多次战斗。
- 保留日志未记录此窗口的死亡/复活。旧日志不是完整底层操作审计，因此未见记录不等于排除所有存储、丢弃或服务端同步异常。

## 已确认的程序缺陷

1. 旧 stop({ logout = true }) 没有参数默认值。GUI 的 runtime.stop() 无参调用立即抛出 TypeError，停止动作、断连、登出均未执行。针对性测试修复前复现了该异常。
2. 管理进程会吞掉停止失败后结束 Worker。游戏连接属于外部 API 服务，Worker 退出不能作为角色已离线的证据。
3. 即使传参，旧流程也先关闭 Tac，等待强制 LLM Reflection 和存盘，最后才断连；模型请求可能拖延游戏断连。

这说明此前重启/编译期间确有失去战斗保护的风险。角色有高生命和恢复效果，界面血量保持824不能证明没有遭受攻击。**是否正是该风险耗尽了四件钻甲，缺少断连窗口内的装备/服务端伤害记录，无法定案。**

## 已实施修复

- stop 的参数增加默认空对象，无参停止可以正常执行。
- 先停止游戏动作并请求游戏断连，再登出和保存本地数据；停止流程不再发起或等待新的 Reflection。
- 记录停机开始、游戏断连接口成功回包、断连失败警告。
- 增加装备基线、装备变化和每32点已损耗耐久分段的本地审计；记录成功/失败的 equip、drop、windowAct 操作。审计只落日志，不调用 LLM、不接管任务。
- 进度文字增加护甲/镐/剑/台分项，保留原本正确的24钻护甲折算公式，只计当前真实持有物和验证设施，不把历史失物伪计为当前资产。
