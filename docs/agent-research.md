# Minecraft Agent 运行效率与架构借鉴

## 参考工作

- [Voyager（Wang et al., 2023）](https://arxiv.org/abs/2305.16291)：把可复用的技能代码、自动课程和环境反馈组合起来，减少每一步都让模型重新规划的开销。
- [ReAct（Yao et al., 2022）](https://arxiv.org/abs/2210.03629)：把观察、行动和结果交替反馈给规划器；规划器不应在动作执行时阻塞实时控制。
- [MineDojo（Fan et al., NeurIPS 2022）](https://arxiv.org/abs/2206.08853)：强调可扩展的任务/技能接口、丰富的环境观测和可持续的长期记忆。
- [Reflexion（Shinn et al., NeurIPS 2023）](https://arxiv.org/abs/2303.11366)：把失败转成短文本经验，在后续决策中复用，而不是立即重复同一条失败路径。
- [SayCan（Ahn et al., 2022）](https://arxiv.org/abs/2204.01691)：语言计划必须经过当前环境与可执行能力的约束，不能只根据语言模型“觉得合理”就执行。

## 本项目中的落地

1. Strategy、Action、Tac 保持分层并行：Strategy 在 Action 执行期间预思考，Tac 只在真实危险附近抢占队列。动作队列仍遵守 API 的单动作互斥约束。
2. 计划动作支持批量入队。队列会按优先级串行执行；同一批次中某一步失败时，剩余步骤会立即取消，避免继续执行已经失效的计划。
3. WorldModel 对观察数据分级缓存：状态和事件保持高频，背包、实体、可见方块和进度按不同频率刷新。这样减少重复观察请求，降低观察请求与动作请求争抢网络/服务端资源造成的卡顿。
4. Action 调试事件记录排队等待时间、执行耗时和队列长度。UI 可以区分“排队慢”和“接口本身慢”，便于后续按数据调参。
5. 挖掘、寻路、MLG、战斗和地形平整继续由确定性脚本执行；模型只选择技能和参数，并通过动作结果与 Reflection 记忆修正下一轮计划。

## 当前限制

赛事 API 明确规定动作互斥，并且一次 `/dig` 会等待服务端完成该方块的挖掘。因此底层挖掘不能安全地并发请求；优化重点是减少多余观察、模型等待和动作之间的空转，而不是向 API 并发发送动作。
